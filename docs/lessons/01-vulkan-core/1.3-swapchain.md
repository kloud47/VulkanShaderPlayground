## 1. Concepts

### 1.1 What a swapchain really is

A swapchain is a small set of images (usually 2–4) that you share with the **presentation
engine** (the OS compositor plus display hardware). Each image is always owned by one side:

```
             vkAcquireNextImageKHR                  vkQueuePresentKHR
 presentation ───────────────────────►  your app  ─────────────────────►  presentation
   engine        "image #2 is yours"    renders     "image #2 is ready"     engine shows it
                 (signals a semaphore   into #2     (waits on a semaphore)
                  when really free)
```

Note two things:
- **Acquire returns an index right away, but the image may not be free yet.** That's why
  acquire signals a *semaphore* that your rendering must wait on (lesson 1.4).
- **You don't choose which image you get.** The index can come back in any order, so code
  that assumes 0, 1, 2, 0, 1, 2 is wrong.

### 1.2 Three questions you ask the surface

| Query | Returns | You use it for |
|---|---|---|
| `vkGetPhysicalDeviceSurfaceCapabilitiesKHR` | min/max image count, current/min/max extent, transforms | image count, extent |
| `vkGetPhysicalDeviceSurfaceFormatsKHR` | list of `{format, colorSpace}` | choosing the format |
| `vkGetPhysicalDeviceSurfacePresentModesKHR` | list of present modes | vsync behavior |

### 1.3 Surface format, and why you want sRGB

Prefer **`VK_FORMAT_B8G8R8A8_SRGB` + `VK_COLOR_SPACE_SRGB_NONLINEAR_KHR`**, and fall back to the
first format in the list.

This choice matters for everything you'll do in GLSL later, so here's why:

- Monitors expect **gamma-encoded** values. A pixel value of 0.5 is *not* displayed at half the
  brightness of 1.0, but at roughly 22%.
- Lighting math (adding lights, `N·L`, blending) is only physically correct in **linear** space.
- With an `_SRGB` format, **your shader writes linear values and the hardware gamma-encodes
  them** when storing. You get correct math and a correct display for free.

You'll see this in 1.4: clearing to `(0.5, 0.5, 0.5)` looks noticeably **lighter** than
mid-gray. The stored byte is about 188, not 128. That isn't a bug; that's the encoding working.
(It also explains a later surprise: in Phase 4, ImGui's colors look washed out unless
they're handled correctly.)

### 1.4 Present modes = vsync behavior

| Mode | Behavior | Tearing | Latency | Notes |
|---|---|---|---|---|
| `FIFO` | Queue of frames, one shown per vblank. CPU blocks when it's full | No | Medium | **Always supported.** Classic vsync |
| `FIFO_RELAXED` | Like FIFO, but a late frame is shown immediately | Sometimes | Medium | |
| `MAILBOX` | Newest frame replaces the waiting one; shown at vblank | No | Low | Renders "as fast as possible" and wastes frames, so it costs power and heat on a laptop |
| `IMMEDIATE` | Shown immediately | Yes | Lowest | Good for measuring raw FPS |

Plan for a `vsync` flag:
- `vsync == true` → `FIFO` (the default: cool, quiet laptop)
- `vsync == false` → `MAILBOX` if available, else `IMMEDIATE`, else `FIFO`

Phase 4 adds a UI checkbox for it, and toggling it recreates the swapchain.

### 1.5 Extent and image count

- **Extent:** if `capabilities.currentExtent.width != UINT32_MAX`, you **must** use
  `currentExtent`. Otherwise the surface lets you choose, so clamp the window's
  **framebuffer size** (lesson 0.2) to `minImageExtent`/`maxImageExtent`. Afterwards, always
  render with `swapchain.extent()`, never the window size. They can differ.
- **Image count:** `minImageCount + 1` (so you're not stuck waiting on the driver), clamped
  to `maxImageCount`. A `maxImageCount` of 0 means "no maximum".

### 1.6 The rest of `VkSwapchainCreateInfoKHR`

| Field | Value | Why |
|---|---|---|
| `imageArrayLayers` | 1 | Not stereo 3D |
| `imageUsage` | `COLOR_ATTACHMENT_BIT \| TRANSFER_DST_BIT` | Render into it; later blit or copy into it |
| `imageSharingMode` | `EXCLUSIVE` | One queue family (lesson 1.2) |
| `preTransform` | `capabilities.currentTransform` | No rotation (matters on phones) |
| `compositeAlpha` | `OPAQUE_BIT_KHR` | The window isn't see-through |
| `clipped` | `VK_TRUE` | Don't care about pixels hidden behind other windows |
| `oldSwapchain` | previous swapchain, or `VK_NULL_HANDLE` | Lets the driver reuse resources during recreation |

### 1.7 Image views

The swapchain owns its `VkImage`s. **Never destroy them yourself.** To render into one, you
need a `VkImageView`: a description of how to interpret the image (2D, this format, color
aspect, mip 0, layer 0). You create one view per image, and you *do* destroy those.

### 1.8 Recreation

The swapchain must be rebuilt when:
- acquire or present returns `VK_ERROR_OUT_OF_DATE_KHR` (must) or `VK_SUBOPTIMAL_KHR` (should),
- the window's framebuffer was resized (your `consumeResizedFlag()`),
- the present mode changes (vsync toggle).

Recipe:
1. If the framebuffer is 0×0 (minimized): `waitEvents()` until it isn't.
2. `vkDeviceWaitIdle`, which is simple and fine for something that happens rarely.
3. Create the **new** swapchain with `oldSwapchain = current`.
4. Destroy the **old** views and the **old** swapchain. (Passing it as `oldSwapchain`
   "retires" it, but doesn't destroy it.)
5. Create views for the new images.

## 2. Build it

### Step 1 — `vk/Swapchain.h`

```cpp
namespace vsp {

class Swapchain {
public:
    void init(VulkanContext& ctx, VkExtent2D framebufferExtent, bool vsync);
    void recreate(VkExtent2D framebufferExtent, bool vsync);
    void shutdown();

    VkSwapchainKHR handle()     const { return m_swapchain; }
    VkFormat       format()     const { return m_format; }
    VkExtent2D     extent()     const { return m_extent; }
    uint32_t       imageCount() const { return static_cast<uint32_t>(m_images.size()); }
    VkImage        image(uint32_t i) const { return m_images[i]; }
    VkImageView    view(uint32_t i)  const { return m_views[i]; }

private:
    void create(VkExtent2D framebufferExtent, bool vsync, VkSwapchainKHR oldSwapchain);
    void destroyViews();

    VulkanContext*           m_ctx       = nullptr;
    VkSwapchainKHR           m_swapchain = VK_NULL_HANDLE;
    VkFormat                 m_format    = VK_FORMAT_UNDEFINED;
    VkColorSpaceKHR          m_colorSpace{};
    VkPresentModeKHR         m_presentMode{};
    VkExtent2D               m_extent{};
    std::vector<VkImage>     m_images;
    std::vector<VkImageView> m_views;
    // 1.4 adds: std::vector<VkSemaphore> m_renderFinished;   (one per image)
};

}
```

Why `create()` takes `oldSwapchain` as a parameter: `init` and `recreate` then share 100% of
the creation code. `init` passes `VK_NULL_HANDLE`, and `recreate` passes the current one,
then cleans up the old one.

### Step 2 — Choosing functions

Write these as free functions in the `.cpp` (in an anonymous namespace). They're pure logic,
easy to read and to test:

```cpp
VkSurfaceFormatKHR chooseSurfaceFormat(const std::vector<VkSurfaceFormatKHR>& available);
VkPresentModeKHR   choosePresentMode(const std::vector<VkPresentModeKHR>& available, bool vsync);
VkExtent2D         chooseExtent(const VkSurfaceCapabilitiesKHR& caps, VkExtent2D framebuffer);
uint32_t           chooseImageCount(const VkSurfaceCapabilitiesKHR& caps);
```

### Step 3 — `create()`
- [ ] query capabilities, formats and present modes
- [ ] choose everything, fill `VkSwapchainCreateInfoKHR` (table in §1.6), `VK_CHECK(vkCreateSwapchainKHR(...))`
- [ ] get the images (two-call idiom with `vkGetSwapchainImagesKHR`)
- [ ] create one `VkImageView` per image (`VK_IMAGE_VIEW_TYPE_2D`, `m_format`, aspect `COLOR`, 1 mip, 1 layer)
- [ ] log: `Swapchain 1600x900  VK_FORMAT_B8G8R8A8_SRGB  VK_PRESENT_MODE_FIFO_KHR  3 images`
      (`string_VkFormat`, `string_VkPresentModeKHR`)

### Step 4 — `recreate()` and `shutdown()`
- [ ] `recreate`: wait idle → keep the old handle → `destroyViews()` → `create(..., old)` →
      `vkDestroySwapchainKHR(old)`
- [ ] `shutdown`: destroy views, then the swapchain. Null the handles. Clear the vectors.

### Step 5 — Hook it up temporarily

Lesson 1.4 creates a `Renderer` that owns the swapchain. For now, put a `Swapchain` in
`Application`, call `init` after the Vulkan context and `shutdown` before it, so you can see
the log line and check for a clean exit.

## 4. Common pitfalls

| Symptom | Cause / fix |
|---|---|
| Validation: `imageExtent` outside min/max | You used the window size instead of `currentExtent`, or forgot to clamp |
| `vkCreateSwapchainKHR` fails while minimized | Extent 0×0. Never create a swapchain with zero size; wait for events instead |
| Validation: destroying a `VkImage` owned by the swapchain | Destroy the **views** only. The swapchain owns the images |
| Everything looks too bright/washed (in 1.4) | Expected with `_SRGB` when you think in non-linear values. See §1.3 |
| Leaked swapchain after a resize | You passed `oldSwapchain` but never destroyed the old one |

## 5. Check your understanding

1. Why does `vkAcquireNextImageKHR` need to signal a semaphore if it already returned an index?
2. What does an `_SRGB` swapchain format do automatically, and why do you want that for lighting?
3. Why is `MAILBOX` not automatically "better" than `FIFO` on a laptop?
4. When must you use `capabilities.currentExtent` instead of your own size?
5. What do you destroy, and what must you **not** destroy, when tearing down a swapchain?

<details><summary>Answers</summary>

1. The index tells you *which* image will be yours, but the presentation engine may still be
   reading it (showing the previous frame). The semaphore signals when it's actually free
   for the GPU to write.
2. It converts the linear values your shaders write into gamma-encoded sRGB on store (and the
   reverse on read). Lighting math is only correct in linear space, and the display expects
   encoded values. The format lets you have both.
3. MAILBOX keeps the GPU rendering frames that are then thrown away, so you burn power and
   heat for no visible benefit (other than latency). FIFO renders only what's displayed.
4. Whenever `currentExtent.width != UINT32_MAX`, which on Windows is basically always. The
   surface dictates the size.
5. Destroy the image views you created and the `VkSwapchainKHR`. Don't destroy the
   `VkImage`s. They belong to the swapchain and go away with it.
</details>
