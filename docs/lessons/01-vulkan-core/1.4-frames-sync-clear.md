## 1. Concepts

### 1.1 Why "frames in flight"

The CPU records commands and the GPU executes them. If the CPU waits for the GPU to finish
every frame before starting the next, each side sits idle half the time:

```
 1 frame in flight:   CPU ███░░░░███░░░░███░░░░          (░ = waiting)
                      GPU ░░░████░░░████░░░████

 2 frames in flight:  CPU ███ ███ ███ ███ ███
                      GPU  ░████ ████ ████ ████          CPU records frame N+1 while GPU runs frame N
```

With **2 frames in flight** the CPU can be at most one frame ahead. Anything the CPU writes
per frame (command buffers now; uniform buffers in 3.2) needs **one copy per frame in flight**,
because frame N+1 must not overwrite data that frame N's GPU work is still reading.

`constexpr uint32_t kMaxFramesInFlight = 2;` More than 2 adds input latency for little gain.

### 1.2 The three sync tools

| Tool | Direction | Use here |
|---|---|---|
| **Fence** (`VkFence`) | GPU → **CPU** | "Has the GPU finished frame N's commands?" The CPU waits before reusing frame N's resources |
| **Binary semaphore** (`VkSemaphore`) | GPU → **GPU**, between queue operations | Acquire → render, and render → present |
| **Pipeline barrier** (`vkCmdPipelineBarrier2`) | Inside a command buffer | Order work, make writes visible, and **transition image layouts** |

(Timeline semaphores, which are core in 1.2, can replace fences and binary semaphores for
most things. Present still needs binary semaphores. They're a stretch goal.)

### 1.3 The frame, step by step

```
frame = m_frames[m_frameIndex]

 1. vkWaitForFences(frame.inFlight)             CPU waits until the GPU finished this slot's last use
 2. vkAcquireNextImageKHR → imageIndex          signals frame.imageAvailable when the image is truly free
      OUT_OF_DATE → recreate swapchain, return  (don't touch the fence!)
 3. vkResetFences(frame.inFlight)               only now: we're certain to submit
 4. vkResetCommandPool(frame.pool)              reuse the command buffer
 5. record:
      barrier   UNDEFINED → COLOR_ATTACHMENT_OPTIMAL
      vkCmdBeginRendering (loadOp = CLEAR, clear color)
      vkCmdEndRendering
      barrier   COLOR_ATTACHMENT_OPTIMAL → PRESENT_SRC_KHR
 6. vkQueueSubmit2:  wait   frame.imageAvailable          @ COLOR_ATTACHMENT_OUTPUT
                     signal renderFinished[imageIndex]    @ COLOR_ATTACHMENT_OUTPUT
                     fence  frame.inFlight
 7. vkQueuePresentKHR: wait renderFinished[imageIndex]
      OUT_OF_DATE / SUBOPTIMAL / window resized → recreate swapchain
 8. m_frameIndex = (m_frameIndex + 1) % kMaxFramesInFlight
```

Two ordering rules in there cause most of the classic bugs:

- **Reset the fence after a successful acquire, not before.** If acquire returns
  `OUT_OF_DATE` and you return early after resetting, nothing will ever signal that fence.
  The next time this slot comes around, `vkWaitForFences` waits forever: a frozen app.
- **On `VK_SUBOPTIMAL_KHR` from acquire, keep going.** The image is acquired and the
  semaphore *will* be signaled. If you bail out to recreate, that semaphore stays signaled
  with nobody waiting on it, which is a validation error. Recreate after presenting instead.

### 1.4 Which semaphore is per what?

This is subtle, and many older tutorials get it wrong:

| Object | Count | Why |
|---|---|---|
| `imageAvailable` semaphore | **per frame in flight** | The fence wait in step 1 proves the previous submit that waited on it has run, so it's safe to reuse |
| `inFlight` fence | **per frame in flight** | Protects that slot's command buffer (and later its uniform buffers) |
| `renderFinished` semaphore | **per swapchain image** | Present waits on it, and **nothing tells you when present has finished with it**. The only guarantee you get is that when the *same image* is acquired again, its previous present is done. So you index it by `imageIndex` |

If you make `renderFinished` per frame in flight instead, recent validation layers report that
you're signaling a semaphore the swapchain may still be using. The Vulkan Guide has a page on
exactly this problem: https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html

Since `renderFinished` is per image, it belongs with the swapchain images: create them in
`Swapchain::create()` and recreate them along with the images.

### 1.5 Image layouts and barriers (synchronization2)

GPUs store images differently depending on how they're used (compressed for rendering,
linear for display, ...). A **layout** names the arrangement, and you **transition** between
them with an image barrier:

```cpp
VkImageMemoryBarrier2 barrier{
    .sType         = VK_STRUCTURE_TYPE_IMAGE_MEMORY_BARRIER_2,
    .srcStageMask  = ...,  .srcAccessMask = ...,   // "wait for THIS work, and make THESE writes available"
    .dstStageMask  = ...,  .dstAccessMask = ...,   // "...before THIS work, with THESE accesses"
    .oldLayout     = ...,  .newLayout     = ...,
    .image         = image,
    .subresourceRange = { VK_IMAGE_ASPECT_COLOR_BIT, 0, 1, 0, 1 },
};
VkDependencyInfo dep{ .sType = VK_STRUCTURE_TYPE_DEPENDENCY_INFO,
                      .imageMemoryBarrierCount = 1, .pImageMemoryBarriers = &barrier };
vkCmdPipelineBarrier2(cmd, &dep);
```

What sync2 improves over the old API: stages and accesses are paired **in the same struct**,
and you call one function for all barrier types.

The two barriers of this frame:

| | Before rendering | After rendering |
|---|---|---|
| `oldLayout → newLayout` | `UNDEFINED → COLOR_ATTACHMENT_OPTIMAL` | `COLOR_ATTACHMENT_OPTIMAL → PRESENT_SRC_KHR` |
| `srcStageMask` | `COLOR_ATTACHMENT_OUTPUT` | `COLOR_ATTACHMENT_OUTPUT` |
| `srcAccessMask` | `NONE` | `COLOR_ATTACHMENT_WRITE` |
| `dstStageMask` | `COLOR_ATTACHMENT_OUTPUT` | `COLOR_ATTACHMENT_OUTPUT` |
| `dstAccessMask` | `COLOR_ATTACHMENT_WRITE` | `NONE` |

Why each of these values?

- **`oldLayout = UNDEFINED`** means "I don't care about the current contents". It's allowed,
  and cheapest, because you clear the whole image anyway. (Once you need the previous
  contents, you'll have to name the real old layout.)
- **Dependency chains through matching stages.** The submit **waits** on `imageAvailable`
  **at stage `COLOR_ATTACHMENT_OUTPUT`**, and barrier 1's `srcStageMask` is also
  `COLOR_ATTACHMENT_OUTPUT`. Because the stages match, the two link up: *image really free →
  layout transition → your writes*. Barrier 2's `dstStageMask` and the submit's **signal**
  stage are also both `COLOR_ATTACHMENT_OUTPUT`. That's the same trick in the other direction:
  *your writes → transition to PRESENT → signal → present*.
- **`dstAccessMask = NONE` for present.** The presentation engine isn't a pipeline stage. The
  semaphore wait in `vkQueuePresentKHR` makes the writes visible to it.

> Many engines use `ALL_COMMANDS` for every stage mask. It's correct but blunt, because it
> stalls more than needed. Learn the precise version now; you can always simplify later.

Write a helper so that you never type a barrier from scratch again:

```cpp
namespace vsp::vkutil {
void transitionImage(VkCommandBuffer cmd, VkImage image,
                     VkImageLayout oldLayout, VkImageLayout newLayout,
                     VkPipelineStageFlags2 srcStage, VkAccessFlags2 srcAccess,
                     VkPipelineStageFlags2 dstStage, VkAccessFlags2 dstAccess,
                     VkImageAspectFlags aspect = VK_IMAGE_ASPECT_COLOR_BIT);
}
```

### 1.6 Dynamic rendering: no render pass, no framebuffer

In your hello-triangle you probably created a `VkRenderPass` and one `VkFramebuffer` per
swapchain image. With Vulkan 1.3 dynamic rendering, you describe the attachments **at record
time**:

```cpp
VkRenderingAttachmentInfo color{
    .sType       = VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO,
    .imageView   = swapchain.view(imageIndex),
    .imageLayout = VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL,
    .loadOp      = VK_ATTACHMENT_LOAD_OP_CLEAR,
    .storeOp     = VK_ATTACHMENT_STORE_OP_STORE,
    .clearValue  = { .color = { { r, g, b, 1.0f } } },
};
VkRenderingInfo info{
    .sType = VK_STRUCTURE_TYPE_RENDERING_INFO,
    .renderArea = { {0, 0}, swapchain.extent() },
    .layerCount = 1,
    .colorAttachmentCount = 1,
    .pColorAttachments = &color,
};
vkCmdBeginRendering(cmd, &info);
// draws go here (Phase 2)
vkCmdEndRendering(cmd);
```

A render with **zero draws** still performs the `loadOp = CLEAR`. That's your clear for this
lesson. Note that layout transitions are now **your** job (that's what the barriers above
are for). With render passes they happened implicitly.

### 1.7 Command pools: one per frame in flight

Give each frame its own `VkCommandPool` with one primary `VkCommandBuffer`. At the start of
the frame (after the fence wait), call `vkResetCommandPool(device, pool, 0)`. That resets
every buffer from the pool at once, cheaply, and needs no special pool flags. Begin the buffer
with `VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT`, since you re-record it every frame.

### 1.8 Name your objects

Before writing the loop, add a debug-name helper to `VkUtils` and use it for everything you
create from now on:

```cpp
void setDebugName(VkDevice device, VkObjectType type, uint64_t handle, const char* name);
// setDebugName(dev, VK_OBJECT_TYPE_SEMAPHORE, (uint64_t)sem, "renderFinished[2]");
```

It calls `vkSetDebugUtilsObjectNameEXT`. Load that function once with `vkGetDeviceProcAddr`
(an extension function, as in 1.1), and do nothing if validation/debug utils is off. From now
on, validation errors and RenderDoc show `renderFinished[2]` instead of a hex number.

### Step 3 — `renderer/Renderer.h`

```cpp
namespace vsp {

constexpr uint32_t kMaxFramesInFlight = 2;

struct FrameData {
    VkCommandPool   commandPool    = VK_NULL_HANDLE;
    VkCommandBuffer commandBuffer  = VK_NULL_HANDLE;
    VkSemaphore     imageAvailable = VK_NULL_HANDLE;
    VkFence         inFlight       = VK_NULL_HANDLE;
};

class Renderer {
public:
    void init(VulkanContext& ctx, Window& window);
    void shutdown();
    void drawFrame(double timeSeconds);

private:
    void createFrames();
    void destroyFrames();
    void recreateSwapchain();

    VulkanContext* m_ctx    = nullptr;
    Window*        m_window = nullptr;
    Swapchain      m_swapchain;
    std::array<FrameData, kMaxFramesInFlight> m_frames{};
    uint32_t       m_frameIndex = 0;
    bool           m_vsync      = true;
};

}
```

(Phase 2 will split `drawFrame` into `beginFrame()` / `endFrame()` so that scene drawing and
ImGui can record in between. For now one function is clearer.)

### Step 4 — `createFrames()` / `destroyFrames()`
- [ ] per frame: command pool (graphics family) → allocate 1 primary buffer → semaphore →
      fence **created signaled** (`VK_FENCE_CREATE_SIGNALED_BIT`)
- [ ] name them all (`"frame[0].inFlight"` ...)

Why signaled? The first `drawFrame` waits on the fence before anything was ever submitted.
An unsignaled fence would block forever.

### Step 5 — `drawFrame()`

Implement §1.3 exactly. Some details:
- Fence wait: `vkWaitForFences(dev, 1, &f.inFlight, VK_TRUE, UINT64_MAX)`.
- Acquire: handle `VK_SUCCESS`, `VK_SUBOPTIMAL_KHR` (continue) and `VK_ERROR_OUT_OF_DATE_KHR`
  (recreate + return) **explicitly**, and `VK_CHECK` anything else.
- Clear color: animate it with `timeSeconds`. For example, each channel is
  `0.5 + 0.5 * sin(t + phase)` with phases 0, 2.09 and 4.19 (120° apart), scaled by about 0.3
  so it isn't blinding.
- Submit with `vkQueueSubmit2`, using `VkSemaphoreSubmitInfo` (wait/signal + stage mask) and
  `VkCommandBufferSubmitInfo` inside a `VkSubmitInfo2`.
- Present: `VkPresentInfoKHR` waits on `m_swapchain.renderFinished(imageIndex)`.
- After present: if the result is `OUT_OF_DATE` or `SUBOPTIMAL`, **or** `m_window->consumeResizedFlag()`,
  call `recreateSwapchain()`.

<details><summary>Hint: the submit structs</summary>

```cpp
VkSemaphoreSubmitInfo wait{
    .sType     = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
    .semaphore = f.imageAvailable,
    .stageMask = VK_PIPELINE_STAGE_2_COLOR_ATTACHMENT_OUTPUT_BIT,
};
VkSemaphoreSubmitInfo signal{ /* renderFinished(imageIndex), same stage */ };
VkCommandBufferSubmitInfo cmdInfo{
    .sType         = VK_STRUCTURE_TYPE_COMMAND_BUFFER_SUBMIT_INFO,
    .commandBuffer = f.commandBuffer,
};
VkSubmitInfo2 submit{
    .sType                    = VK_STRUCTURE_TYPE_SUBMIT_INFO_2,
    .waitSemaphoreInfoCount   = 1, .pWaitSemaphoreInfos   = &wait,
    .commandBufferInfoCount   = 1, .pCommandBufferInfos   = &cmdInfo,
    .signalSemaphoreInfoCount = 1, .pSignalSemaphoreInfos = &signal,
};
VK_CHECK(vkQueueSubmit2(queue, 1, &submit, f.inFlight));
```
</details>

## 4. Break it on purpose (10 minutes, very instructive)

Make each change, run, read the message, then **undo it**:

| Experiment | What you should learn |
|---|---|
| Delete the first barrier (UNDEFINED → COLOR_ATTACHMENT) | Validation reports the image is in the wrong layout when used. Layouts are tracked strictly |
| Make `renderFinished` a single per-frame semaphore instead of per image | The swapchain-semaphore-reuse warning from §1.4 (it may need a few frames or a resize to appear) |
| Move `vkResetFences` **before** acquire, and use a 2-second timeout in `vkWaitForFences` (log on `VK_TIMEOUT`) | Resize a few times. When acquire returns `OUT_OF_DATE` (log it to confirm your driver does), the early return leaves a reset fence that never gets signaled, and your timeout log fires. With `UINT64_MAX` the app would freeze |
| Set `dstAccessMask = NONE` in the first barrier, with sync validation on | Expect a `SYNC-HAZARD-WRITE-AFTER-WRITE` report: the layout transition is a write, and without a memory dependency the clear's writes aren't ordered after it |

## 5. Common pitfalls

| Symptom | Cause / fix |
|---|---|
| App freezes after a resize | Fence reset before an early return (see experiment 3) |
| Validation: semaphore already signaled / not waited on | You returned early on `SUBOPTIMAL` from acquire. Continue the frame instead |
| Black or garbage screen, no errors | Rendering into the wrong view (`m_frameIndex` used instead of `imageIndex`) |
| Validation spam only after resize | `renderFinished` semaphores weren't recreated with the new images, or the image count changed |
| Crash on close | Destroying while the GPU is busy. Call `vkDeviceWaitIdle` before shutdown |
| Clear color looks lighter than expected | sRGB working as intended (lesson 1.3 §1.3) |

## 6. Check your understanding

1. Why is the `inFlight` fence created signaled?
2. Why must `vkResetFences` come *after* a successful acquire?
3. Why is `imageAvailable` per frame in flight, while `renderFinished` is per swapchain image?
4. Explain how the acquire semaphore's wait stage and the first barrier's `srcStageMask` work
   together.
5. What does `oldLayout = UNDEFINED` promise the driver, and when would it be wrong?
6. With FIFO and the GPU idle, which call blocks the CPU to keep you at the refresh rate?
7. What does dynamic rendering replace, and what job does it hand back to you?

<details><summary>Answers</summary>

1. The first wait on each slot happens before anything has been submitted. A signaled fence
   lets it pass through.
2. If acquire fails (`OUT_OF_DATE`) you return without submitting. A reset fence would then
   never be signaled, and the next wait on that slot would hang.
3. Before reusing `imageAvailable[f]`, you wait on fence `f`, which proves the submit that
   consumed it has executed. For `renderFinished`, present consumes it and nothing tells you
   when that's done. The only guarantee is that when the same image is re-acquired, its
   previous present has finished. So it's keyed by image.
4. The submit's semaphore wait blocks the `COLOR_ATTACHMENT_OUTPUT` stage of the submitted work
   until the image is free. The barrier's first scope is the same stage, so the dependencies
   chain: semaphore → layout transition → attachment writes.
5. That you don't need the current contents, so the driver may discard them. It would be wrong
   if you used `loadOp = LOAD` or otherwise needed what was previously in the image.
6. Usually `vkAcquireNextImageKHR` or `vkWaitForFences`. When all images are queued for
   display, the CPU blocks until one is released at the next vblank.
7. It replaces `VkRenderPass` and `VkFramebuffer` objects (attachments are described at record
   time in `VkRenderingInfo`). In return you handle image layout transitions yourself with
   barriers.
</details>
