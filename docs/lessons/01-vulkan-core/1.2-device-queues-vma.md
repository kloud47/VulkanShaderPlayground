## 1. Concepts

### 1.1 The surface comes first

A `VkSurfaceKHR` is Vulkan's handle to "the place on screen where images can be presented".
You create it **before** choosing a GPU, because not every GPU and queue family can present
to every surface, and you need to ask.

```cpp
glfwCreateWindowSurface(instance, window.handle(), nullptr, &m_surface);
```

It belongs to the **instance** (destroy it with `vkDestroySurfaceKHR` before the instance).

### 1.2 Choosing a GPU on a hybrid laptop

`vkEnumeratePhysicalDevices` returns both of your GPUs. **The order means nothing.** The AMD
switchable-graphics layer from lesson 1.1 can even reorder the list based on Windows' graphics
settings, so never just take `devices[0]`.

Use two passes:

**Pass 1: hard requirements (reject the device if any fail)**

| Requirement | How to check |
|---|---|
| Vulkan ≥ 1.3 | `VkPhysicalDeviceProperties::apiVersion >= VK_API_VERSION_1_3` |
| `VK_KHR_swapchain` | `vkEnumerateDeviceExtensionProperties` |
| A queue family with **graphics and present** | `queueFlags & VK_QUEUE_GRAPHICS_BIT` and `vkGetPhysicalDeviceSurfaceSupportKHR` |
| Required features | `vkGetPhysicalDeviceFeatures2` (see §1.4) |
| At least one surface format and present mode | `vkGetPhysicalDeviceSurfaceFormatsKHR` / `...PresentModesKHR` count > 0 |

**Pass 2: score the survivors, then pick the highest**

| | Score |
|---|---|
| `VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU` | +1000 |
| `VK_PHYSICAL_DEVICE_TYPE_INTEGRATED_GPU` | +100 |
| Device-local VRAM in GB (sum of heaps with `VK_MEMORY_HEAP_DEVICE_LOCAL_BIT`) | +GB, as a tie-breaker |

Both of your GPUs pass Pass 1, and the RTX 3050 wins Pass 2. The stretch goal lets you force
the iGPU. It's worth doing: when your app runs correctly on two vendors' drivers, you know
you're relying on the spec and not on one driver's tolerance.

### 1.3 Queue families and queues

A **queue family** is a group of identical hardware queues with the same capabilities
(graphics, compute, transfer, ...). You submit command buffers to a **queue**.

For this project: **one queue, from a family that supports graphics and presenting.** Every
desktop GPU has one. (Any family with `GRAPHICS` also implicitly supports transfer, and
graphics families also support compute on all common hardware.) Dedicated transfer or
async-compute queues are an optimization for later. The compute particles in Phase 9 might
want one.

> **Edge case:** the spec allows a GPU where no single family has both graphics and present.
> If you find no such family, throw a clear error. Supporting separate families is a stretch
> goal, and it adds ownership transfers to everything.

### 1.4 Features: query, then explicitly enable

Vulkan features are **off unless you enable them**, even ones that are core in 1.3. Dynamic
rendering and synchronization2 are core in 1.3, so they need no extension, but you still
have to turn them on when creating the device. The mechanism is a `pNext` chain (as in 1.1):

```
VkPhysicalDeviceFeatures2              ── .features      : core 1.0 features (samplerAnisotropy, fillModeNonSolid)
   └─ pNext ─► VkPhysicalDeviceVulkan12Features  (nothing yet; bufferDeviceAddress, descriptorIndexing later)
                  └─ pNext ─► VkPhysicalDeviceVulkan13Features  (dynamicRendering, synchronization2)
```

You use the **same struct types twice**:
1. **Query**: pass a chain to `vkGetPhysicalDeviceFeatures2`, which fills in what the GPU supports.
2. **Enable**: build a second chain with only the features you want set to `VK_TRUE`, and
   pass it as `VkDeviceCreateInfo::pNext`. In that case `pEnabledFeatures` must be `nullptr`.

Features this project enables now:

| Feature | Struct | Used in |
|---|---|---|
| `dynamicRendering` | `Vulkan13Features` | 1.4: render without `VkRenderPass`/`VkFramebuffer` |
| `synchronization2` | `Vulkan13Features` | 1.4: `vkCmdPipelineBarrier2`, `vkQueueSubmit2` |
| `samplerAnisotropy` | `VkPhysicalDeviceFeatures` | 6.2: sharper textures at grazing angles |
| `fillModeNonSolid` | `VkPhysicalDeviceFeatures` | 4.2: wireframe mode |

Enabling them all now means you won't have to come back to device creation for a while.

### 1.5 The logical device

`VkDevice` is your session with one GPU. Nearly everything from here on (buffers, images,
pipelines, command pools) is created from it. To create it you pass:
- the queue create infos (family index, count = 1, priority = 1.0f),
- the device extensions (`VK_KHR_SWAPCHAIN_EXTENSION_NAME`),
- the feature chain from §1.4.

Don't set device layers. They've been deprecated since Vulkan 1.0.13, and instance layers
apply to devices automatically.

Then get the queue with `vkGetDeviceQueue(device, family, 0, &queue)`.

### 1.6 Why VMA

Vulkan exposes GPU memory as **heaps** (physical pools: VRAM, system RAM) and **memory types**
(heap + properties: `DEVICE_LOCAL`, `HOST_VISIBLE`, `HOST_COHERENT`, `HOST_CACHED`). Doing it
by hand, you would:
- choose the right type for every buffer and image,
- suballocate, because drivers limit the number of allocations
  (`maxMemoryAllocationCount`, often 4096) and each allocation is slow,
- handle alignment, mapping, defragmentation...

The **Vulkan Memory Allocator** does all of this. You create one `VmaAllocator` per device,
and from Phase 2 on you'll call `vmaCreateBuffer`/`vmaCreateImage` with a simple usage hint.
You still need to understand heaps and types (the exercise below helps), but you don't write
an allocator.

```cpp
VmaAllocatorCreateInfo info{ /* physicalDevice, device, instance, vulkanApiVersion = VK_API_VERSION_1_3 */ };
VK_CHECK(vmaCreateAllocator(&info, &m_allocator));
```

> Designated-initializer trap: `VmaAllocatorCreateInfo` declares `physicalDevice`, then
> `device`, then (much later) `instance`, then `vulkanApiVersion`. Initialize them in that order.

## 2. Build it

### Step 1 — Extend `VulkanContext`

Add members and accessors:

```cpp
VkSurfaceKHR     m_surface        = VK_NULL_HANDLE;
VkPhysicalDevice m_physicalDevice = VK_NULL_HANDLE;
VkDevice         m_device         = VK_NULL_HANDLE;
VkQueue          m_graphicsQueue  = VK_NULL_HANDLE;
uint32_t         m_graphicsFamily = UINT32_MAX;
VmaAllocator     m_allocator      = VK_NULL_HANDLE;
VkPhysicalDeviceProperties m_gpuProperties{};   // limits are handy later
```

`init()` order: `createInstance → createDebugMessenger → createSurface → pickPhysicalDevice → createDevice → createAllocator`.
`shutdown()` order: the reverse.

### Step 2 — `pickPhysicalDevice()`

Structure it so that each piece is testable and easy to log:

```cpp
struct GpuCandidate {
    VkPhysicalDevice device;
    uint32_t         graphicsFamily;
    int              score;
    std::string      rejectReason;   // empty = suitable
};
GpuCandidate evaluateGpu(VkPhysicalDevice gpu) const;
```

- [ ] Enumerate GPUs and evaluate each one.
- [ ] **Log every GPU**, including rejected ones and why, for example:
      `[1] AMD Radeon(TM) Graphics  integrated  Vulkan 1.3.260  score 100`
- [ ] Pick the highest score. If none are suitable, throw with the reject reasons in the message.
- [ ] Store the properties of the chosen GPU.

<details><summary>Hint: checking required features without a wall of ifs</summary>

Query into the chain, then check the members you care about:

```cpp
VkPhysicalDeviceVulkan13Features f13{ .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_3_FEATURES };
VkPhysicalDeviceVulkan12Features f12{ .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_2_FEATURES, .pNext = &f13 };
VkPhysicalDeviceFeatures2        f2 { .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_FEATURES_2,        .pNext = &f12 };
vkGetPhysicalDeviceFeatures2(gpu, &f2);

if (!f13.dynamicRendering) return reject("no dynamicRendering");
```

Keep "what I require" in **one place** (a small struct or function) that is used both for
checking and for enabling, so the two lists can't drift apart.
</details>

### Step 3 — `createDevice()`

- [ ] `VkDeviceQueueCreateInfo` for `m_graphicsFamily`, 1 queue, `float priority = 1.0f`
- [ ] the enable chain (Features2 → 12 → 13) with your required features set to `VK_TRUE`
- [ ] `VkDeviceCreateInfo{ .pNext = &features2, ..., .pEnabledFeatures = nullptr }`
- [ ] `vkGetDeviceQueue`

### Step 4 — `createAllocator()`

- [ ] `vmaCreateAllocator` with physical device, device, instance and `VK_API_VERSION_1_3`
- [ ] (No flags for now. When you enable `bufferDeviceAddress` later, you'll also pass
      `VMA_ALLOCATOR_CREATE_BUFFER_DEVICE_ADDRESS_BIT`.)

### Step 5 — Explore your memory (exercise, about 20 lines)

Call `vkGetPhysicalDeviceMemoryProperties` on the chosen GPU and log every **heap** (size in
MB, `DEVICE_LOCAL` or not) and every **memory type** (heap index + property flags). Use
`string_VkMemoryPropertyFlags()` from the enum string helper.

Answer these from your own output (write the answers in a comment, they're useful later):
1. Which heap is your ~4 GB of VRAM?
2. Is there a small heap that is **both** `DEVICE_LOCAL` and `HOST_VISIBLE`? (On many NVIDIA
   GPUs there's one of about 200 MB, or the whole VRAM with Resizable BAR.) What could you
   use memory like that for?
3. Which type would a staging buffer (CPU writes, GPU copies from it) use?

### Step 6 — Log useful limits

Log these from `m_gpuProperties.limits`. They come up in later lessons:
`maxPushConstantsSize` (3.2), `minUniformBufferOffsetAlignment` (3.2),
`maxSamplerAnisotropy` (6.2), `timestampPeriod` (Phase 9 GPU timers).

## 4. Common pitfalls

| Symptom | Cause / fix |
|---|---|
| `VK_ERROR_FEATURE_NOT_PRESENT` from `vkCreateDevice` | You enabled a feature the GPU doesn't support. Your Pass 1 check doesn't match your enable list (see the hint) |
| Validation: `pEnabledFeatures` must be NULL | You passed both `pEnabledFeatures` and a `VkPhysicalDeviceFeatures2` in `pNext` |
| Validation complains about `sType` | A struct in a chain has the wrong `sType` (copy-paste!), or you forgot to set it |
| Only one GPU listed | Normal on desktops; on your laptop see the AMD layer note in 1.1 |
| Crash in `vmaCreateAllocator` | `VMA_IMPLEMENTATION` missing, or `device` / `physicalDevice` swapped |

## 5. Check your understanding

1. Why must the surface exist before you pick a physical device?
2. Dynamic rendering is "core in 1.3". Why do you still have to enable it?
3. Why can't you trust the order of `vkEnumeratePhysicalDevices` on your laptop?
4. Name two jobs VMA does for you that raw `vkAllocateMemory` doesn't.
5. When the device is created with `VkPhysicalDeviceFeatures2` in `pNext`, what must
   `pEnabledFeatures` be, and why?

<details><summary>Answers</summary>

1. Present support is per queue family **per surface** (`vkGetPhysicalDeviceSurfaceSupportKHR`
   takes the surface), and surface formats and present modes are per GPU + surface too.
2. "Core" means no extension is needed and the API is always available. Features are still
   opt-in, so drivers can avoid overhead for apps that don't use them, and validation can
   catch accidental use.
3. The order is implementation-defined. On hybrid systems, layers like
   `VK_LAYER_AMD_switchable_graphics` actively reorder or filter it.
4. Picking a memory type for each resource. Suballocating many resources from a few large
   blocks (staying under `maxMemoryAllocationCount`). Also handling alignment and
   persistent mapping, plus stats and budget queries.
5. `nullptr`. Core 1.0 features now go in `VkPhysicalDeviceFeatures2::features`. Supplying
   both is ambiguous, so it's invalid usage.
</details>
