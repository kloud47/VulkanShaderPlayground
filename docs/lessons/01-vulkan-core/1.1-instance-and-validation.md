## Phase 1 overview

You've drawn a triangle before, so Phase 1 isn't about getting pixels on screen at any cost.
It's about building a **correct, reusable frame loop** that the rest of the project stands on.
Here's every object Phase 1 creates, and who owns it:

```
VulkanContext (1.1–1.2)                    Swapchain (1.3)            Renderer (1.4)
───────────────────────                    ───────────────            ──────────────
VkInstance ─────────┬── VkDebugUtilsMessengerEXT
                    └── VkSurfaceKHR ─────► VkSwapchainKHR
VkPhysicalDevice (chosen GPU)                  ├─ VkImage ×N (owned by swapchain)
VkDevice ───────────┬── VkQueue (graphics+present)  ├─ VkImageView ×N
                    ├── VmaAllocator               └─ VkSemaphore renderFinished ×N
                    │
                    └─────────────────────────────────────────► per frame in flight (×2):
                                                                 VkCommandPool, VkCommandBuffer,
                                                                 VkSemaphore imageAvailable,
                                                                 VkFence inFlight
```

Teardown happens in exactly the reverse order. Keep this map open while you work through Phase 1.

## 1. Concepts

### 1.1 The loader, layers and drivers on *your* machine

Your code never talks to the GPU driver directly. Every `vk*` call goes through the
**Vulkan loader** (`vulkan-1.dll`), which forwards it through any **layers** and on to an
**ICD** (Installable Client Driver, meaning the GPU vendor's driver):

```
 your app
    │  vkCreateInstance, vkCmdDraw...
    ▼
 vulkan-1.dll (loader)
    │
    ├─► implicit layers   (installed by other software, always on unless disabled)
    │      e.g. VK_LAYER_AMD_switchable_graphics   ← you have this one (hybrid laptop)
    ├─► explicit layers   (only when YOU enable them)
    │      e.g. VK_LAYER_KHRONOS_validation        ← you'll enable this one
    ▼
 ICDs:  NVIDIA driver  → GeForce RTX 3050 Laptop GPU  (Vulkan 1.4)
        AMD driver     → AMD Radeon Graphics (iGPU)   (Vulkan 1.3)
```

Your laptop has **two ICDs** and the AMD **switchable graphics implicit layer**. When this
project was planned, `vulkaninfoSDK --summary` on your machine printed:

> `Layer VK_LAYER_AMD_switchable_graphics uses API version 1.3 which is older than the application specified API version of 1.4.`

That's the loader telling you an implicit layer is older than the API version that was
requested. You'll request **1.3**, so it won't appear for this app. It's still a good example
of how layers sit between you and the driver.

> If one of your GPUs ever goes missing from the device list, this layer is the usual
> suspect. Setting the environment variable `DISABLE_LAYER_AMD_SWITCHABLE_GRAPHICS_1=1`
> disables it for a test run.

### 1.2 What the instance is

`VkInstance` is your connection to the loader. It decides:
- **which API version** your app targets (`VkApplicationInfo::apiVersion`),
- **which instance layers** are active (validation),
- **which instance extensions** are on (surface support, debug utils).

About `apiVersion = VK_API_VERSION_1_3`: it's the **highest** Vulkan version your app intends
to use. It isn't a request that fails if a device is older. A 1.1+ loader won't fail instance
creation over it, but you'll only use 1.3 features on devices that support 1.3, and lesson 1.2
checks for that explicitly. Before creating the instance, call `vkEnumerateInstanceVersion`
and refuse to start if the loader itself is below 1.3.

### 1.3 Validation layers

`VK_LAYER_KHRONOS_validation` checks every call against the spec, including object lifetimes,
parameter values, and (when enabled) synchronization hazards. Vulkan drivers do almost no
error checking themselves. Without validation, a bug can mean anything from "works on
NVIDIA" to "hangs on AMD" to "blue screen". **It's on in every Debug build of this project.**

You decide at compile time: Debug builds don't define `NDEBUG`, RelWithDebInfo builds do.

```cpp
#ifndef NDEBUG
constexpr bool kEnableValidation = true;
#else
constexpr bool kEnableValidation = false;
#endif
```

### 1.4 `VK_EXT_debug_utils` and the messenger

Validation messages need somewhere to go. `VK_EXT_debug_utils` lets you register a
**callback** that receives every message:

```cpp
static VKAPI_ATTR VkBool32 VKAPI_CALL debugCallback(
    VkDebugUtilsMessageSeverityFlagBitsEXT      severity,   // VERBOSE / INFO / WARNING / ERROR
    VkDebugUtilsMessageTypeFlagsEXT             types,      // GENERAL / VALIDATION / PERFORMANCE
    const VkDebugUtilsMessengerCallbackDataEXT* data,       // data->pMessage is the text
    void*                                       userData);  // your pointer (unused for now)
```

- Always **return `VK_FALSE`**. (`VK_TRUE` asks the layer to abort the call, which is only
  useful for testing layers.)
- **Put a breakpoint on errors.** In Debug, call `__debugbreak()` when
  `severity >= ..._ERROR_BIT_EXT`. The callback runs *inside* the bad Vulkan call, so the
  call stack shows you exactly which line of your code caused the error. This is the single
  most useful Vulkan debugging trick.

The same extension gives you `vkSetDebugUtilsObjectNameEXT` (names in error messages and
RenderDoc, see 1.4) and `vkCmdBeginDebugUtilsLabelEXT` (groups in RenderDoc).

### 1.5 Extension functions must be loaded

`vkCreateDebugUtilsMessengerEXT` isn't exported by `vulkan-1.lib`. You have to ask for it
at runtime:

```cpp
auto fn = reinterpret_cast<PFN_vkCreateDebugUtilsMessengerEXT>(
    vkGetInstanceProcAddr(instance, "vkCreateDebugUtilsMessengerEXT"));
```

Do this for create and destroy. (In the future, a loader library such as **volk** does this
for every function and makes calls slightly faster. Not needed yet.)

### 1.6 `pNext` chains: Vulkan's extension mechanism

Almost every Vulkan create-info struct has `const void* pNext`. You extend a call by chaining
more structs onto it, each with its own `sType` so the driver knows what it's looking at:

```
VkInstanceCreateInfo { sType, pNext ──► VkDebugUtilsMessengerCreateInfoEXT { sType, pNext = nullptr, ... } }
```

Here's the first real use. If you chain the messenger create-info into
`VkInstanceCreateInfo::pNext`, validation can report problems **during `vkCreateInstance` and
`vkDestroyInstance`**, when your normal messenger doesn't exist yet or has already been
destroyed. You'll chain feature structs the same way in 1.2.

### 1.7 `VK_CHECK`

Write a macro, not a function. A macro can capture the **expression text** (`#expr`) along
with `__FILE__` and `__LINE__`:

```
[error] vkCreateInstance(&info, nullptr, &m_instance) failed: VK_ERROR_LAYER_NOT_PRESENT (VulkanContext.cpp:87)
```

`string_VkResult()` comes from `<vulkan/vk_enum_string_helper.h>`, which ships with the SDK.
Wrap the body in `do { ... } while (0)` so the macro behaves like a single statement after an
`if`.

> **C++ note:** `std::source_location` can replace `__FILE__`/`__LINE__` in a function, but
> nothing except a macro can stringize the expression. That's why every Vulkan codebase has
> a macro here.

## 2. Build it

### Step 1 — `vk/VkCheck.h`
- [ ] `#include <vulkan/vulkan.h>`, `<vulkan/vk_enum_string_helper.h>`, `core/Log.h`, `<cstdlib>`
- [ ] `VK_CHECK(expr)`: evaluate once into a local, and if it's not `VK_SUCCESS`, log the
      expression, result string, file and line, then `std::abort()`

### Step 2 — `vk/VulkanContext.h`

This class grows in 1.2. Design it with that in mind:

```cpp
namespace vsp {

struct VulkanContextDesc {
    const char* appName          = "Vulkan Shader Playground";
    bool        enableValidation = kEnableValidation;
};

class VulkanContext {
public:
    void init(const VulkanContextDesc& desc, Window& window);
    void shutdown();

    VkInstance instance() const { return m_instance; }
    // 1.2 adds: physicalDevice(), device(), graphicsQueue(), graphicsQueueFamily(), allocator(), surface()

private:
    void createInstance(const VulkanContextDesc& desc);
    void createDebugMessenger();

    VkInstance               m_instance       = VK_NULL_HANDLE;
    VkDebugUtilsMessengerEXT m_debugMessenger = VK_NULL_HANDLE;
    bool                     m_validation     = false;
};

}
```

(Non-copyable, with an asserting destructor. See [ARCHITECTURE.md §4](../../ARCHITECTURE.md).)

### Step 3 — `createInstance()`

- [ ] `vkEnumerateInstanceVersion` → log it (`1.4.341` on your machine). Throw if it's below 1.3.
- [ ] Build the **layer list**. If validation is on, check `vkEnumerateInstanceLayerProperties`
      for `"VK_LAYER_KHRONOS_validation"`. If it's missing, **warn and continue without it**
      rather than crashing (a user might not have the SDK).
- [ ] Build the **extension list**: start from `glfwGetRequiredInstanceExtensions`, and add
      `VK_EXT_DEBUG_UTILS_EXTENSION_NAME` when validation is on. Check each one against
      `vkEnumerateInstanceExtensionProperties` and throw a clear error if one is missing.
- [ ] Log the final layers and extensions.
- [ ] Fill a `VkDebugUtilsMessengerCreateInfoEXT` (write a helper
      `makeDebugMessengerInfo()`, since you'll use it twice) and chain it into `pNext` when
      validation is on.
- [ ] `VK_CHECK(vkCreateInstance(...))`.

Messenger settings to use:

| Field | Value | Why |
|---|---|---|
| `messageSeverity` | `WARNING \| ERROR` (add `INFO` temporarily if curious) | `VERBOSE`/`INFO` are very noisy |
| `messageType` | `GENERAL \| VALIDATION \| PERFORMANCE` | |
| `pfnUserCallback` | your `debugCallback` | |

<details><summary>Hint: the two-call enumeration idiom (you've done it before; here's a reusable shape)</summary>

```cpp
uint32_t count = 0;
vkEnumerateInstanceLayerProperties(&count, nullptr);
std::vector<VkLayerProperties> layers(count);
vkEnumerateInstanceLayerProperties(&count, layers.data());
```

**C++ exercise:** write one template that works for every `vkEnumerate*` / `vkGet*` with this
shape, so you can write `auto layers = enumerate<VkLayerProperties>(vkEnumerateInstanceLayerProperties);`.
</details>

<details><summary>Hint: the dangling-pointer trap</summary>

`ppEnabledExtensionNames` is `const char* const*`. If you build a `std::vector<const char*>` from
`std::string`s that go out of scope, those pointers dangle. GLFW's strings and the
`*_EXTENSION_NAME` macros live forever, so store only those (or keep the `std::string`s alive
until `vkCreateInstance` returns).
</details>

### Step 4 — `createDebugMessenger()`

- [ ] If validation is off, return early.
- [ ] Load `vkCreateDebugUtilsMessengerEXT` with `vkGetInstanceProcAddr`, and throw if it's `nullptr`.
- [ ] Create it with the same `makeDebugMessengerInfo()`.

`debugCallback`:
- [ ] map severity to `log::warn` / `log::error`
- [ ] include `data->pMessageIdName` (for example `VUID-vkDestroyInstance-instance-00629`).
      Paste these IDs into a search engine and they take you straight to the spec rule.
- [ ] `__debugbreak()` on errors in Debug builds (`#ifdef _MSC_VER` + `#ifndef NDEBUG`)

### Step 5 — `shutdown()`
- [ ] Destroy the messenger (loaded the same way), then the instance. Set both to `VK_NULL_HANDLE`.

### Step 6 — wire it into `Application`
- [ ] Add `VulkanContext m_vk;` after `m_window` (members are constructed in declaration order).
- [ ] Constructor: `m_vk.init({}, m_window);`
- [ ] Destructor: `m_vk.shutdown();` The body of `~Application` runs **before** member
      destructors, so Vulkan is torn down while the window still exists. That's the
      order you want.

## 3. Checkpoint ✅

1. Run in **x64 Debug**. The console shows something like:
   ```
   [info] Vulkan loader version 1.4.341
   [info] Validation: ON
   [info] Instance extensions: VK_KHR_surface, VK_KHR_win32_surface, VK_EXT_debug_utils
   [info] Vulkan instance created (API 1.3)
   ```

2. **Prove that validation works.** Temporarily comment out the messenger destroy in
   `shutdown()`. On exit you should get an **error** mentioning
   `VUID-vkDestroyInstance-instance-00629` (the messenger was not destroyed), and the debugger
   should **break inside your callback**. Look at the call stack and find your `shutdown()` in it.
   Then remove the comment.
   *Question:* which messenger reported that error, if you never destroyed yours? (Think
   about §1.6.)
3. Run in **x64 Release**: no validation, no messages, same window.
4. No validation output on a normal exit.

## 4. Common pitfalls

| Symptom | Cause / fix |
|---|---|
| `VK_ERROR_LAYER_NOT_PRESENT` | Validation layer not installed, or Vulkan Configurator is active and overriding layers. Close it (or check its layer configuration) and retry |
| `VK_ERROR_EXTENSION_NOT_PRESENT` | Typo, or you asked for `VK_EXT_debug_utils` without the validation layer available. Use the macro, not a string |
| `vkCreateDebugUtilsMessengerEXT` is `nullptr` | `VK_EXT_debug_utils` isn't in the enabled extension list |
| Callback never fires | Severity mask excludes the messages, or your messenger is created but the `pNext` chain one isn't (or the reverse) |
| Garbage in extension names | Dangling `const char*`. See the hint in Step 3 |

## 5. Explore: Vulkan Configurator

Run `D:\Vulkan\Bin\vkconfig-gui.exe` (Vulkan Configurator; `vkconfig.exe` next to it is the
command-line version). It can override layer settings for **every** Vulkan app while it's
active. Try:
- The **Synchronization** validation preset (or the "synchronization" option in the
  validation layer settings): turns on synchronization validation. You'll want it on for
  lesson 1.4, where it catches barrier mistakes that ordinary validation can't see.
- **Best Practices**: performance and portability advice (noisier, some vendor-specific).
- **Message filtering**: mute a message ID you've decided is fine.

Remember that vkconfig's overrides apply while it's running. If behavior differs between your
machine and a friend's, check whether vkconfig is open.

## 6. Check your understanding

1. What's the difference between an implicit and an explicit layer? Name one of each on your machine.
2. Why is the messenger create-info chained into `VkInstanceCreateInfo::pNext` *and* used to
   create a separate messenger?
3. Why can't you call `vkCreateDebugUtilsMessengerEXT` directly the way you call `vkCreateInstance`?
4. Your app sets `apiVersion = VK_API_VERSION_1_3`. Your AMD iGPU supports 1.3.260 and your
   RTX 3050 supports 1.4.x. What does that number control, and what doesn't it control?
5. Why should the debug callback return `VK_FALSE`?

<details><summary>Answers</summary>

1. Implicit layers are enabled by their installer through the registry/manifest and are active
   without your code asking (`VK_LAYER_AMD_switchable_graphics`). Explicit layers must be
   requested by name (`VK_LAYER_KHRONOS_validation`).
2. The separate messenger only exists between its own create and destroy calls. The chained
   one covers `vkCreateInstance` and `vkDestroyInstance` themselves. That's why the leak in
   checkpoint step 2 was still reported.
3. It's an extension function. The loader library only exports core functions, so extension
   entry points must be fetched at runtime with `vkGetInstanceProcAddr` (or a loader such as volk).
4. It's the highest API version your app will use. It doesn't force devices to be 1.3. You
   still have to check each physical device's `apiVersion` (lesson 1.2), and on each device
   you may only use functionality up to the lower of the two versions.
5. `VK_TRUE` asks the layer to abort the Vulkan call with `VK_ERROR_VALIDATION_FAILED_EXT`.
   That changes your app's behavior, which only makes sense when you're testing layers.
</details>
