## 1. Why this setup

**CMake** describes *what* to build: targets, sources, dependencies. Visual Studio, Ninja,
CLion, and VS Code can all build from it. **vcpkg** in *manifest mode* reads a `vcpkg.json`
in your project and builds or installs exactly those libraries, at pinned versions, the first
time you configure. You never set include or lib paths by hand, and a fresh clone builds on
any machine.

| Comes from | What |
|---|---|
| **Vulkan SDK** (`D:\Vulkan`, `VULKAN_SDK` env var) | Vulkan headers + loader lib, validation layers, `glslc`, Vulkan Configurator, `vkcube` |
| **vcpkg** | GLFW, GLM, VMA now; stb, Dear ImGui and Assimp in later phases |

Why not take GLM and VMA from the SDK too? Your SDK install didn't include those optional
components, and that's fine: vcpkg pins their versions per project, which is better anyway.

## 3. Build it

### Step 1 — Folder layout and git

Create this structure. Git doesn't track empty folders, so put an empty `.gitkeep` file in
each empty one.

```
VulkanShaderPlayground/
├─ docs/            (already here)
├─ assets/models/
├─ assets/textures/
├─ shaders/
└─ src/
   ├─ app/
   ├─ core/
   └─ vk/
```

Then, in a terminal at the project root:

```bash
git init
```

Create `.gitignore`:

```gitignore
# CMake / Ninja build output (presets put everything in out/)
out/
build/

# Visual Studio
.vs/
*.user
CMakeUserPresets.json

# vcpkg (manifest mode installs inside out/, this is a safety net)
vcpkg_installed/

# Generated
*.spv
*.rdc
```

> **Keep the project path short.** vcpkg builds libraries in deep subfolders, and Windows
> still has a 260-character path limit in many tools. `D:\Game_Dev\Projects\VulkanShaderPlayground`
> is fine. A path twice that long broke a glfw build while this setup was being tested.

### Step 2 — vcpkg manifest

Open **Developer PowerShell for VS 2026**, either from the Start menu or in VS via
*Tools → Command Line → Developer PowerShell*. This shell has `VCPKG_ROOT` set to VS's
bundled vcpkg, and has `cl.exe` and `ninja` on `PATH`.

```bash
cd D:\Game_Dev\Projects\VulkanShaderPlayground
```

```bash
vcpkg new --application
```

```bash
vcpkg add port glfw3 glm vulkan-memory-allocator
```

You now have two files. Open both and read them:

- **`vcpkg.json`**: *what* you depend on (`glfw3`, `glm`, `vulkan-memory-allocator`).
- **`vcpkg-configuration.json`**: *where* the packages come from. It holds a
  `"baseline": "<commit sha>"`, a commit of the official vcpkg registry. That commit fixes
  every library's version, so your build is reproducible: in a year, this project still gets
  GLFW 3.4, not whatever is newest. Upgrading means changing that baseline on purpose.

Later phases add ports the same way (`vcpkg add port stb`, `imgui`, `assimp`).

### Step 3 — `CMakePresets.json`

Presets are named build configurations that VS, VS Code and the command line all understand.
This file is pure configuration, so type it as-is and make sure you understand each field:

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "windows-base",
      "hidden": true,
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/out/build/${presetName}",
      "installDir": "${sourceDir}/out/install/${presetName}",
      "toolchainFile": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake",
      "cacheVariables": {
        "CMAKE_C_COMPILER": "cl.exe",
        "CMAKE_CXX_COMPILER": "cl.exe"
      },
      "architecture": { "value": "x64", "strategy": "external" },
      "condition": { "type": "equals", "lhs": "${hostSystemName}", "rhs": "Windows" }
    },
    {
      "name": "x64-debug",
      "displayName": "x64 Debug",
      "inherits": "windows-base",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "Debug" }
    },
    {
      "name": "x64-release",
      "displayName": "x64 Release (with debug info)",
      "inherits": "windows-base",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "RelWithDebInfo" }
    }
  ],
  "buildPresets": [
    { "name": "x64-debug", "configurePreset": "x64-debug" },
    { "name": "x64-release", "configurePreset": "x64-release" }
  ]
}
```

| Field | Meaning |
|---|---|
| `hidden: true` | `windows-base` is only for inheriting. It doesn't show up in VS's dropdown |
| `generator: Ninja` | Fast parallel builds. VS ships Ninja, so no install needed |
| `binaryDir` | Each preset builds into its own folder under `out/` (git-ignored) |
| `toolchainFile` | **The line that turns vcpkg on.** vcpkg's toolchain reads `vcpkg.json` and installs packages during configure |
| `architecture … external` | Tells VS to set up the x64 MSVC environment *for* Ninja |
| `Debug` | No optimization, validation layers **on** (no `NDEBUG`) |
| `RelWithDebInfo` | Optimized but debuggable, validation **off** (`NDEBUG` defined). Your "how fast is it really" build |

### Step 4 — `CMakeLists.txt`

Same deal: type it and read the comments.

```cmake
cmake_minimum_required(VERSION 3.25)
project(VulkanShaderPlayground VERSION 0.1.0 LANGUAGES CXX)

# --- Language ---------------------------------------------------------------
set(CMAKE_CXX_STANDARD 20)            # designated initializers, std::format, concepts
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# --- Dependencies -----------------------------------------------------------
find_package(Vulkan REQUIRED COMPONENTS glslc)          # from the SDK (VULKAN_SDK)
find_package(glfw3 CONFIG REQUIRED)                     # from vcpkg
find_package(glm CONFIG REQUIRED)                       # from vcpkg
find_package(VulkanMemoryAllocator CONFIG REQUIRED)     # from vcpkg

# --- Executable -------------------------------------------------------------
# GLOB is convenient for a learning project: new files are picked up on the next
# build. (Big projects list files explicitly for reproducibility.)
file(GLOB_RECURSE VSP_SOURCES CONFIGURE_DEPENDS src/*.cpp src/*.h)
add_executable(VulkanShaderPlayground ${VSP_SOURCES})

target_include_directories(VulkanShaderPlayground PRIVATE src)

target_link_libraries(VulkanShaderPlayground PRIVATE
    Vulkan::Vulkan
    glfw
    glm::glm
    GPUOpen::VulkanMemoryAllocator)

target_compile_definitions(VulkanShaderPlayground PRIVATE
    GLM_FORCE_DEPTH_ZERO_TO_ONE    # Vulkan depth range is [0,1], not OpenGL's [-1,1] (lesson 3.1)
    GLM_FORCE_RADIANS
    NOMINMAX                       # stop <windows.h> from defining min/max macros
    WIN32_LEAN_AND_MEAN
    VSP_ASSETS_DIR="${CMAKE_SOURCE_DIR}/assets"
    VSP_SHADERS_DIR="${CMAKE_SOURCE_DIR}/shaders")

if(MSVC)
    target_compile_options(VulkanShaderPlayground PRIVATE /W4 /permissive- /utf-8)
endif()
```

Things worth understanding here:
- **Imported targets carry everything.** Linking `glfw` adds GLFW's include path, its `.lib`,
  and its defines. That's modern CMake: you never write `include_directories(...)` for a
  dependency.
- **Where did those target names come from?** When vcpkg installs a port it prints *usage*
  text, for example `glfw3 provides CMake targets: find_package(glfw3 CONFIG REQUIRED) …
  target_link_libraries(main PRIVATE glfw)`. When you add a library later, read that text
  in VS's Output window (or run `vcpkg install` in the Developer PowerShell) to get the
  exact names.
- **`VSP_ASSETS_DIR` / `VSP_SHADERS_DIR`** bake absolute source paths into the exe, so the
  app finds `assets/` and `shaders/` regardless of the working directory. That's ideal
  for a dev tool, and essential for hot reload in Phase 7, where you edit files in the
  source tree.
- **`glslc` component**: not used until Phase 2, but `find_package` fails early if it's
  missing, which is better than finding out later.
- **DLLs:** vcpkg's default triplet `x64-windows` builds GLFW as a DLL. The toolchain copies
  `glfw3.dll` next to your exe automatically after each build.

### Step 5 — `src/vk/VmaUsage.cpp`

VMA is a single-header library. The header contains the declarations everywhere, and the
implementation **only** in the one `.cpp` that defines `VMA_IMPLEMENTATION` before including
it. Exactly one translation unit may do this, otherwise you get duplicate symbols:

```cpp
#define VMA_IMPLEMENTATION
#include <vk_mem_alloc.h>
```

(stb_image works the same way in Phase 6.)

### Step 6 — `src/main.cpp`: hello dependencies (you write this)

Write a `main()` that proves every dependency is wired up. It should:

1. Call `vkEnumerateInstanceVersion` and print the loader version using the
   `VK_API_VERSION_MAJOR/MINOR/PATCH` macros.
2. Create a `glm::vec3{1, 2, 3}` and print `glm::length` of it.
3. Print `string_VkResult(VK_SUCCESS)` (from `<vulkan/vk_enum_string_helper.h>`).
4. `glfwInit()`, print `glfwGetVersionString()` and `glfwVulkanSupported()`, then `glfwTerminate()`.
5. Print `VSP_ASSETS_DIR`.

Use `std::format` for output. Include `<vk_mem_alloc.h>` here as well, just to prove the
header resolves.

## 5. Common pitfalls

| Symptom | Fix |
|---|---|
| Configure error: toolchain file `/scripts/buildsystems/vcpkg.cmake` not found | `VCPKG_ROOT` is empty. Open the folder from VS (not a plain terminal), or create a git-ignored `CMakeUserPresets.json` (see below) |
| `Could not find a package configuration file provided by "glfw3"` | The toolchain line is missing or misspelled, or `vcpkg.json` doesn't list the port. Fix it, then **Project → Delete Cache and Reconfigure** |
| `No CMAKE_CXX_COMPILER could be found` from a terminal | You're in a plain PowerShell. Use **Developer PowerShell for VS 2026** |
| `C1083: Cannot open compiler generated file` while building a port | Path too long. Move the project to a shorter path |
| Red squiggles everywhere in VS | IntelliSense hasn't seen a successful configure yet. Wait for the CMake output to say "Generating done" |
| You changed `vcpkg.json` and nothing happened | **Project → Delete Cache and Reconfigure** |

<details><summary>Fallback: CMakeUserPresets.json that sets VCPKG_ROOT explicitly</summary>

User presets are for machine-specific settings and are git-ignored. Put this file next to
`CMakePresets.json`, then pick **my x64 Debug** in VS:

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "my-x64-debug",
      "displayName": "my x64 Debug",
      "inherits": "x64-debug",
      "environment": {
        "VCPKG_ROOT": "C:/Program Files/Microsoft Visual Studio/18/Community/VC/vcpkg"
      }
    }
  ]
}
```
</details>

## 6. Check your understanding

1. What's the difference between `vcpkg.json` and `vcpkg-configuration.json`?
2. Which single line in `CMakePresets.json` makes vcpkg run during configure?
3. Why does exactly one `.cpp` define `VMA_IMPLEMENTATION`? What happens with two? With zero?
4. Why are Vulkan headers and the loader taken from the SDK instead of vcpkg?
5. Debug vs RelWithDebInfo: which one defines `NDEBUG`, and why does that matter for Vulkan
   (hint: lesson 1.1)?

<details><summary>Answers</summary>

1. `vcpkg.json` lists *what* you depend on. `vcpkg-configuration.json` says *where* packages come
   from (the registry) and pins *which versions* through the baseline commit.
2. `"toolchainFile": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake"`.
3. That `.cpp` compiles the implementation. With two you get duplicate symbol linker errors
   (LNK2005). With zero you get unresolved externals (LNK2019) as soon as you call
   `vmaCreateAllocator`.
4. The SDK also provides the validation layers, `glslc`, and Vulkan Configurator. Keeping
   headers, loader and layers from one SDK version avoids mismatches.
5. RelWithDebInfo (and Release) define `NDEBUG`. The project uses it to switch validation
   layers off in optimized builds.
</details>
