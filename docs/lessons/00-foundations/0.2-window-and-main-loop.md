state, render. Getting this skeleton right now means every later lesson just plugs a new
subsystem into `Application`, with no rewiring.

## 2. Concepts

### 2.1 What GLFW does (and doesn't do) for Vulkan

GLFW was born as an OpenGL helper. By default it creates an OpenGL context with every window.
For Vulkan you must turn that off:

```cpp
glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API);
```

With Vulkan, GLFW gives you three things:
1. A window and its events (keyboard, mouse, resize, close).
2. The list of instance extensions needed to present to that window
   (`glfwGetRequiredInstanceExtensions` → `VK_KHR_surface`, `VK_KHR_win32_surface`), used in 1.1.
3. A `VkSurfaceKHR` for the window (`glfwCreateWindowSurface`), used in 1.2.

Everything else (the swapchain, presentation) is yours.

### 2.2 Window size ≠ framebuffer size

GLFW reports two sizes:

| Function | Unit | Use for |
|---|---|---|
| `glfwGetWindowSize` | screen coordinates | window placement, mouse math |
| `glfwGetFramebufferSize` | **pixels** | **the swapchain extent** |

On Windows, screen coordinates *are* pixels, so the two are normally equal. On macOS (Retina)
and Linux/Wayland they differ by the display scale. The swapchain must match the framebuffer
**in pixels**, so get into the habit now: anything renderer-related asks for the
*framebuffer* size, which is correct on every platform.

Your laptop probably runs Windows display scaling at 125% or 150%. That doesn't change the
two sizes, but it means a 1600×900-pixel window looks *smaller* than other apps. Two related
tools for later:
- the `GLFW_SCALE_TO_MONITOR` window hint makes GLFW multiply the requested size by the
  monitor scale;
- `glfwGetWindowContentScale` returns the scale (for example 1.5). You'll use it in Phase 4
  so ImGui text isn't tiny.

When minimized, the framebuffer size becomes **0 × 0**. You can't create a 0×0 swapchain, so
lesson 1.3 will wait while minimized. Design for it now.

### 2.3 C callbacks → C++ objects: the user-pointer pattern

GLFW callbacks are plain C function pointers, so you can't pass a member function. The
standard trick:

```cpp
glfwSetWindowUserPointer(m_window, this);                       // store 'this'
glfwSetFramebufferSizeCallback(m_window, [](GLFWwindow* w, int, int) {
    auto* self = static_cast<Window*>(glfwGetWindowUserPointer(w)); // get it back
    self->m_resized = true;
});
```

A capture-less lambda converts to a function pointer, so this compiles. You'll reuse this
pattern for key, mouse and scroll callbacks in 3.4.

### 2.4 The main loop and delta time

```
while (!window.shouldClose()):
    window.pollEvents()        // process input / resize / close events (non-blocking)
    dt = now - last; last = now
    update(dt)                 // animations, camera...   (later)
    render()                   // Vulkan                  (Phase 1)
```

- **`glfwPollEvents`** returns immediately. That's right for a renderer that redraws every frame.
- **`glfwWaitEvents`** blocks until an event arrives. You'll use it while the window is minimized.
- Measure time with `std::chrono::steady_clock` (monotonic, never jumps) or `glfwGetTime()`.
  Animations must multiply by `dt`, never assume a fixed frame rate.

> **Expect a huge FPS number (thousands) in this lesson**, with one CPU core at 100%. Nothing
> limits the loop yet. In Phase 1 the swapchain's FIFO (vsync) mode will throttle it to your
> display's refresh rate.

### 2.5 Ownership of `glfwInit` / `glfwTerminate`

GLFW is a global library. This app has exactly one window, so it's fine for `Window` to call
`glfwInit()` in its constructor and `glfwTerminate()` in its destructor. Set the error callback
**before** `glfwInit` so you see init errors too.

## 3. Build it

### Step 1 — `core/Log.h`: a tiny logger

Write a header with `vsp::log::info`, `warn`, `error` that format with `std::format` and print
a prefix such as `[info]`.

The trick to get **compile-time-checked** format strings (like `std::print`) is
`std::format_string<Args...>` as the parameter type:

```cpp
template <typename... Args>
void info(std::format_string<Args...> fmt, Args&&... args);
```

Requirements:
- `error` goes to `std::cerr`, the others to `std::cout`.
- Bonus: colored prefixes. Windows Terminal and the VS console understand ANSI codes such
  as `\x1b[33m` (yellow) and `\x1b[0m` (reset).

<details><summary>Hint: body of one function</summary>

```cpp
std::cout << "[info] " << std::format(fmt, std::forward<Args>(args)...) << '\n';
```
</details>

### Step 2 — `core/Window.h/.cpp`

Design the interface first. A suggested shape:

```cpp
namespace vsp {

struct WindowDesc {
    std::string title  = "Vulkan Shader Playground";
    int         width  = 1600;
    int         height = 900;
    bool        resizable = true;
};

class Window {
public:
    explicit Window(const WindowDesc& desc);
    ~Window();
    Window(const Window&) = delete;
    Window& operator=(const Window&) = delete;

    bool shouldClose() const;
    void pollEvents();
    void waitEvents();                  // used while minimized (1.3)

    struct Extent { uint32_t width, height; };
    Extent framebufferExtent() const;   // pixels!
    bool   isMinimized() const;         // framebuffer is 0x0

    bool   consumeResizedFlag();        // returns true once after each resize
    void   setTitle(const std::string& title);

    GLFWwindow* handle() const { return m_window; }

private:
    GLFWwindow* m_window = nullptr;
    bool        m_resized = false;
};

} // namespace vsp
```

Why `consumeResizedFlag()` instead of a getter plus a reset? The renderer asks "did a resize
happen since I last checked?" and the answer has to reset atomically with the read. One
function does both, so you can't forget the reset.

Implementation checklist:
- [ ] `glfwSetErrorCallback` → logs `code` + `description` with `log::error`
- [ ] `glfwInit()`; throw `std::runtime_error` if it fails
- [ ] `glfwVulkanSupported()`; throw if false (this means no Vulkan loader/ICD was found)
- [ ] hints: `GLFW_CLIENT_API = GLFW_NO_API`, `GLFW_RESIZABLE`
- [ ] `glfwCreateWindow`; throw on `nullptr`
- [ ] user pointer + framebuffer-size callback sets `m_resized`
- [ ] key callback: **Esc** → `glfwSetWindowShouldClose(w, GLFW_TRUE)`
- [ ] destructor: `glfwDestroyWindow`, then `glfwTerminate`

Include order matters: either `#define GLFW_INCLUDE_VULKAN` before `<GLFW/glfw3.h>`, or include
`<vulkan/vulkan.h>` first. Pick one and put it in a single place (for example a small
`core/GlfwInclude.h`) so every file includes GLFW the same way.

### Step 3 — `app/Application.h/.cpp`

```cpp
namespace vsp {

class Application {
public:
    Application();      // creates the window (later: Vulkan, renderer, UI...)
    ~Application();     // calls shutdown order (later)
    void run();         // the main loop

private:
    void updateTitle(double dt);

    Window m_window;
    // Phase 1 adds: VulkanContext m_vk; Renderer m_renderer;
};

}
```

`run()` checklist:
- [ ] loop until `m_window.shouldClose()`
- [ ] `pollEvents()` first thing in each frame
- [ ] compute `dt` in seconds as a `double` with `std::chrono::steady_clock`
- [ ] keep a running `m_time` (total seconds). Lesson 1.4 animates the clear color with it.
- [ ] `updateTitle(dt)`: count frames, and **every 0.5 s** set the title to
      `Vulkan Shader Playground | 1234 FPS | 0.81 ms`, then reset the counters.
      (Updating the title every frame is slow, because `SetWindowText` is a Win32 call.)

### Step 4 — `main.cpp`

Replace the smoke test. `main` becomes:

## 5. Common pitfalls

| Symptom | Cause |
|---|---|
| `glfwVulkanSupported()` returns false | No Vulkan loader found. Reinstall the GPU driver; check that `vulkaninfoSDK --summary` works |
| Window flashes and closes | An exception was thrown. Put a breakpoint in the `catch` in `main` |
| Callback crashes with `nullptr` | You called `glfwGetWindowUserPointer` before setting it |
| Designated initializer compile error | Fields out of declaration order (C++20 requires that order) |
| Title updates freeze the window | You update it every frame. Throttle it to 0.5 s |

## 6. Check your understanding

1. Why do we tell GLFW `GLFW_NO_API`? What would happen without it?
2. You create a 1600×900 window on Windows at 150% scaling, with no special hints. What do
   `glfwGetWindowSize` and `glfwGetFramebufferSize` return? Which one feeds the swapchain, and
   why does that choice still matter on Windows?
3. Why can a capture-less lambda be passed to `glfwSetFramebufferSizeCallback` but a capturing
   one can't?
4. Why is `steady_clock` a better choice than `system_clock` for frame timing?

<details><summary>Answers</summary>

1. Otherwise GLFW creates an OpenGL context for the window. That wastes resources, and an
   OpenGL context bound to a window can interfere with creating a Vulkan swapchain for it.
2. Both return 1600×900, because on Windows screen coordinates are pixels. (With
   `GLFW_SCALE_TO_MONITOR` both would be 2400×1350.) The swapchain uses the **framebuffer**
   size. It happens to match here, but on macOS/Wayland it wouldn't, and the framebuffer
   size is also the one that becomes 0×0 when minimized. Code that uses it is correct
   everywhere.
3. Only capture-less lambdas convert implicitly to a plain function pointer. A capturing
   lambda carries state, so it's an object, not a function.
4. `system_clock` follows wall-clock time, which can jump (NTP sync, the user changing the
   clock). `steady_clock` only ever moves forward at a constant rate.
</details>
